## 简介

我们在项目中出于多种目的使用排队论：

- 客户服务响应能力

- 项目管理看板规划

- 进程间通信消息队列

- DevOps 持续部署流水线

### 客户服务响应能力

例如，我们希望分析客户如何请求销售帮助和支持帮助，以及我们的响应速度有多快。

相关产品例如 [Salesforce](https://wikipedia.org/wiki/Salesforce)、[LiveChat](https://wikipedia.org/wiki/LiveChat)、[Zendesk](https://wikipedia.org/wiki/Zendesk)。

### 项目管理看板规划

例如，我们希望跟踪一个新功能构想从设计到交付过程中的前置时间和进展时间。

相关产品例如 [Asana](<https://wikipedia.org/wiki/Asana_(software)>)、[Jira](<https://wikipedia.org/wiki/Jira_(software)>)、[Microsoft Project](https://wikipedia.org/wiki/Microsoft_Project)。

### 进程间通信消息队列

例如，当一个程序向另一个程序发送请求时，我们希望最大化吞吐量并最小化压力。

相关产品例如 [RabbitMQ](https://wikipedia.org/wiki/RabbitMQ)、[ActiveMQ](https://wikipedia.org/wiki/Apache_ActiveMQ)、[ZeroMQ](https://wikipedia.org/wiki/ZeroMQ)。

### DevOps 持续部署流水线

例如，我们希望确保持续集成服务器有足够的容量来测试并部署我们的软件。

相关产品例如 [Jenkins](<https://wikipedia.org/wiki/Jenkins_(software)>)、[Bamboo](<https://wikipedia.org/wiki/Bamboo_(software)>)、[Azure DevOps](https://wikipedia.org/wiki/Microsoft_Visual_Studio#Azure_DevOps)。

## 排队术语

排队术语是一个很大的话题。本节介绍我们常用的一些术语。在示例中，我们以顾客排队等候为例。

### 队列类型与服务类型

队列类型与服务类型描述队列如何选择要处理的条目。

- 先进先出（FIFO）：服务等待时间最长的顾客。

- 后进先出（LIFO）：服务等待时间最短的顾客。

- 优先级：根据顾客的优先级服务；优先级可以基于身份、紧急程度、付费等。

- 最短作业优先（SJF）：服务所需服务量最少的顾客。

- 最长作业优先（LJF）：服务所需服务量最多的顾客。

- 最短剩余处理时间（SRPT）：与 SJF 类似，但新到达的短作业可以抢占正在服务的较长作业。

- 轮转（Round Robin）：为每位顾客服务一个短时间片，然后转向下一位顾客，如此循环。

- 分时，又称处理器共享（PS）：同时为所有人服务；服务能力在所有等待者之间平均分配。

SJF 和 SRPT 能使平均等待时间最小，但可能让长作业无限期地“饿死”，因此实际系统常常加入老化机制或优先级上限。

## 排队论符号

排队论使用希腊字母作为符号。

我们的团队使用一些常见的符号；我们还添加了一些对软件项目有帮助的自定义符号。

我们的表示法及各符号的含义：

| 我们的表示法 | 含义 |
| ------ | -- |
| κ（kappa） | 系统中的条目数，即等待中的条目加上正在处理的条目 |
| λ（lambda） | 进入系统的条目的到达率 |
| χ（chi） | 离开系统的条目的离开率 |
| μ（mu） | 服务率，又称容量：单个服务台在忙碌时的工作速度 |
| ρ（rho） | 利用率：服务台处于忙碌状态的时间比例，λ / (c μ) |
| α（alpha） | 成功率：观测到的产出中结果正确的部分 |
| β（beta） | 失败率：观测到的产出中结果错误的部分 |
| δ（delta） | 完成率：成功 + 失败，即已获得服务的条目，无论结果正确与否 |
| σ（sigma） | 跳过率：进入系统后未经服务就离开的条目 |
| ε（epsilon） | 错误比率：β / δ = β / (α + β) |
| τ（tau） | 在系统中的时间，又称前置时间 |
| ω（omega） | 等待时间，又称在队列中的时间 |
| φ（phi） | 工作时间，又称在处理器中的时间，又称服务时间 |
| θ（theta） | 两次完成之间的步进时间；稳态下平均步进时间 ≈ 1 / χ |

### 计数

我们经常对条目计数，并使用以下符号：

- κ（kappa）：系统中的条目计数，即等待中的条目加上正在处理的条目。

![示意图：系统中有 κ 个条目](https://queue-theory.github.io/images/queue-theory-kappa-item-count.svg)

示例：

- κ = 10 表示恰好 10 个。

- κ ≈ 10 表示大约 10 个。

- κ < 10 表示少于 10 个。

- κ > 10 表示多于 10 个。

- κ ≪ 10 表示远少于 10 个。

- κ ≫ 10 表示远多于 10 个。

计数 κ（kappa）是某一时刻的快照。

平均计数 κ̅（kappa加横线）是对某一特定时间段内的测量值取平均的计算结果，例如连续两周每小时测量一次。

### 到达率与服务率、离开率

最重要的符号：

- λ（lambda）：到达率。衡量条目进入系统的速度有多快。

- μ（mu）：服务率，又称容量。衡量单个服务台在忙碌时处理条目的速度。

- χ（chi）：离开率。衡量条目离开系统的速度有多快。

![示意图：条目以速率 λ 到达，以速率 μ 获得服务，以速率 χ 离开](https://queue-theory.github.io/images/queue-theory-lambda-arrival-mu-service-chi-departure.svg)

单服务台传统队列的一般规律示例：

- λ < μ 表示到达率小于服务率；队列是稳定的，即队列长度围绕一个有限的平均值波动。

- λ = μ 表示到达率等于服务率；只要存在任何随机性，队列就会漂移并无限增长。

- λ > μ 表示到达率大于服务率；队列稳定增长，每单位时间约增加 λ − μ 个条目。

“λ = μ 能使队列保持同样长度”这一直觉，只有在到达和服务像节拍器一样完全规律时才成立。真实的到达是突发的，因此空闲期间损失的空闲时间永远无法弥补，队列会在下一次突发时增长。

请注意，有些排队论从业者用“服务率”表示观测到的产出，而不是容量；参见[服务率的歧义](#服务率的歧义)。

### 利用率，又称交通强度

概括一个队列的最重要符号：

- ρ（rho）：利用率，即服务台处于忙碌状态的时间比例 = λ / μ（单服务台），或 λ / (c μ)（c 个服务台）

示例：

- ρ < 1 表示服务台有空余容量；队列是稳定的。ρ 越接近 1，等待越长；参见[利用率曲线](#利用率曲线)。

- ρ = 1 表示服务台一直忙碌；队列不稳定并无限增长。

- ρ > 1 表示到达超过容量；队列越来越长。

### 吞吐率：离开率、完成率、成功率、失败率、跳过率

吞吐率衡量观测到的产出，即实际离开队列的条目。吞吐率大致分为五类：

- χ（chi）：离开率。衡量条目离开系统的速度有多快。

- α（alpha）：成功率。衡量每单位时间结果正确的条目数，例如正确、完整、被接受。

- β（beta）：失败率。衡量每单位时间结果错误的条目数，例如不正确、不完整、被拒绝。

- δ（delta）：完成率。衡量每单位时间有多少条目获得服务。

- σ（sigma）：跳过率。衡量每单位时间进入队列后未经服务就离开的条目数，例如放弃、中途离开。

![示意图：离开率 χ = 完成率 δ + 跳过率 σ；完成率 δ = 成功率 α + 失败率 β](https://queue-theory.github.io/images/queue-theory-chi-departure-delta-done-alpha-success-beta-failure-sigma-skip.svg)

完成率 = 成功率 + 失败率：

- δ = α + β（读作：delta 等于 alpha 加 beta）

总率 = 完成率 + 跳过率：

- χ = δ + σ（读作：chi 等于 delta 加 sigma）

总率 = 成功率 + 失败率 + 跳过率：

- χ = α + β + σ（读作：chi 等于 alpha 加 beta 加 sigma）

计入 χ 的每个条目都曾进入系统，因此在稳态下总率等于到达率：χ ≈ λ。这就是为什么吞吐率衡量的是产出，而不是容量。

### 服务率的歧义

根据语境和从业者的不同，“服务率”一词既可以指“总率”，也可以指“成功率”。

这有其历史根源，可能导致混淆和错误，尤其是在需要大量跟踪失败和跳过的排队论应用场景中。

- 理论视角：服务率是纯粹的速度度量（例如每秒作业数），不论作业是成功、失败还是跳过等。

- 处理视角：服务率包括队列花时间处理的所有内容，即成功或失败，但不包括跳过。

- 技术视角：在软件工程等应用领域，服务率只衡量成功，而错误率衡量失败，跳过率衡量跳过。

因此，我们保留 μ 表示容量，并在它之外增加观测到的产出率，而不是取代它：

- μ（mu）：服务率，又称容量。衡量单个服务台在忙碌时处理条目的速度。

- χ（chi）：离开率。衡量条目离开系统的速度有多快。

- α（alpha）：成功率。衡量每单位时间结果正确的条目数，例如正确、完整、被接受。

为什么不用 χ 或 α 取代 μ？在稳定的队列中，每个进入的条目最终都会离开，因此 χ ≈ λ。于是无论负载多大，λ / χ ≈ 1，这完全无法说明服务台有多忙。利用率需要容量：ρ = λ / (c μ)，它等于服务台处于忙碌状态的时间比例。

### 跳过率

跳过率的详细说明：

- σ（sigma）：跳过率。衡量有多少条目进入队列后未经处理就离开。

跳过是指条目进入队列后，在没有经过任何实质处理的情况下离开：

- 放弃：顾客开始排队后，因任何原因离开。

- 中途离开（reneging）：已经等待过的顾客因为浪费了太多时间而决定离开。

有两种相关行为不算跳过：

- 止步（balking）：顾客因为预计等待时间过长而决定不加入队列。止步的条目从未进入系统，因此位于系统边界之外：它不计入 λ、χ 或 σ。如果止步很重要（例如丢失的销售），请把它们作为被拒之门外的到达单独计数。

- 换队（jockeying）：顾客仍留在系统中；顾客在并行队列（例如收银通道）之间切换，试图缩短等待时间。

### 错误比率

概括队列成功情况的最重要符号：

- ε（epsilon）：错误比率 = 失败数 / 完成数 = β / δ = β / (α + β)

跳过不计入，因为被跳过的条目从未被服务，所以既不算对也不算错。请通过 σ 单独跟踪跳过。

![示意图：错误比率 ε 是失败率 β 除以完成率 δ](https://queue-theory.github.io/images/queue-theory-delta-done-alpha-success-beta-failure-epsilon-error.svg)

示例：

- ε = 0 表示没有错误。

- ε = 0.1 表示 10% 的服务有错误。

- ε = 1 表示每次服务都有错误。

### 前置时间、等待时间、工作时间、步进时间

我们跟踪四种时间：

- τ（tau）：在系统中的时间，又称前置时间，又称从开始到结束。

- θ（theta）：步进时间 = 从一次完成到下一次完成；一个步进时间是一个间隔，平均步进时间是这些间隔的平均值

- ω（omega）：等待时间 = 未进行实际工作的时间，又称挂起时间

- φ（phi）：工作时间 = 实际工作所花的时间，又称处理时间

![示意图：前置时间 τ，等待时间 ω，工作时间 φ，步进时间 θ](https://queue-theory.github.io/images/queue-theory-tau-total-time-equals-omega-wait-time-phi-work-time-theta-step-time.svg)

示例：

- τ = 5 秒 表示一个条目进入系统，5 秒后离开系统。

- ω = 4 秒 表示一个条目在队列中等待 4 秒，然后开始工作。

- φ = 1 秒 表示一个条目需要 1 秒的工作，然后完成。

- θ = 1 秒 表示一次完成与下一次完成之间间隔 1 秒。

关系：

- τ = ω + φ：前置时间等于等待时间加工作时间。在示例中，5 秒 = 4 秒 + 1 秒。

- 平均 θ ≈ 1 / χ：在稳态下，平均步进时间是总率的倒数。单个间隔几乎说明不了速率，许多间隔的平均值才能说明。在示例中，如果平均步进时间为 1 秒，则 χ ≈ 每秒 1 个条目。

### 肯德尔符号

肯德尔符号是排队论的另一种符号体系，写作 A/S/c/K/N/D：

- A：到达过程，即到达间隔时间的分布。

- S：服务过程，即服务时间的分布。

- c：服务台数量。

- K：容量，即系统中允许的最大条目数（包括等待中和正在服务的），超过后新到达者将被拒绝。

- N：总体，即潜在顾客的数量。

- D：排队规则，即队列类型，例如 FIFO 或 LIFO。

A 和 S 的常用字母：

- M：马尔可夫，又称无记忆，即指数分布时间，由泊松到达产生。

- D：确定性，即固定时间。

- G：一般，即任意分布。

省略后三项时，默认值为 K = ∞、N = ∞、D = FIFO。例如，“M/M/1”表示泊松到达、指数分布服务时间、一个服务台、容量无限、总体无限、先进先出。

此外：

- n：系统中的条目数。

## 排队数学

数学部分使用教科书符号，便于与其他资料对照：S 是平均服务时间，即我们的 φ；μ = 1 / S 是单个服务台的容量。

### 利用率曲线

排队论中最重要的结论：当利用率接近 100% 时，等待时间会无限增长，而且越到最后增长越快。

对于 M/M/1 队列，设 S 为平均服务时间：

- 前置时间 τ = S / (1 − ρ)

- 等待时间 ω = S × ρ / (1 − ρ)

| 利用率 ρ | 前置时间 τ | 等待时间 ω |
| -------- | ---------- | ---------- |
| 50%      | 2 × S      | 1 × S      |
| 70%      | 3.3 × S    | 2.3 × S    |
| 80%      | 5 × S      | 4 × S      |
| 90%      | 10 × S     | 9 × S      |
| 95%      | 20 × S     | 19 × S     |
| 99%      | 100 × S    | 99 × S     |

示例：一次代码评审需要 1 小时的工作。如果评审者 80% 的时间都在忙，一次评审从请求到完成大约需要 5 小时。如果评审者 95% 的时间都在忙，则大约需要 20 小时，尽管评审者只忙了 15 个百分点。

这就是为什么“让每个人 100% 忙碌”会导致很长的前置时间，也是下面的[洞见](#洞见)警告不要按高利用率做计划的原因。

### 金曼公式

金曼公式，又称 VUT 方程，用于近似任意到达分布和服务分布的单服务台队列（G/G/1）的等待时间：

- ω ≈ (ρ / (1 − ρ)) × ((ca² + cs²) / 2) × S

三个因子是：

- U：利用率因子 ρ / (1 − ρ)，即上面的利用率曲线。

- V：变异性因子 (ca² + cs²) / 2，其中 ca 是到达间隔时间的变异系数，cs 是服务时间的变异系数。变异系数是标准差除以均值。

- T：时间因子 S，即平均服务时间。

示例：对于 M/M/1 队列，ca = cs = 1，所以 V = 1，此时公式给出的等待时间与利用率曲线相同。如果让工作条目更加均匀，例如拆分大工单使 cs 从 1 降到接近 0，那么 V 降到约 0.5，在相同利用率下等待时间大约减半。

金曼公式揭示了减少等待时间的三个杠杆：

- 降低利用率，例如增加容量或限制在制品数量。

- 降低变异性，例如使用更小的批次、更均匀的工作条目或更平稳的到达。

- 缩短服务时间，例如通过自动化。

### 合并队列与 Erlang C

一个共享队列供多个服务台服务，优于每个服务台各自一个队列。这就是为什么银行用一条队伍对应多个柜员，也是为什么共享支持队列胜过按客服人员划分的队列。

示例：两个服务台处理每个条目各需 1 小时，条目总到达率为每小时 1.6 个，因此利用率为 80%。

- 分开的队列：每个服务台都是一个每小时到达 0.8 个的 M/M/1 队列，因此前置时间为 1 / (1 − 0.8) = 5 小时。

- 合并的队列：两个服务台共享一个 M/M/2 队列，前置时间约为 2.8 小时，减少了约 44%，人员和工作量都不变。

Erlang C 公式计算到达的条目在 M/M/c 队列中必须等待的概率，其中提供负载 a = λ / μ，利用率 ρ = a / c：

- P(等待) = ((aᶜ / c!) / (1 − ρ)) / (Σₖ₌₀ᶜ⁻¹ (aᵏ / k!) + (aᶜ / c!) / (1 − ρ))

- 等待时间 ω = P(等待) / (c μ − λ)

客户服务团队使用 Erlang C 来决定需要安排多少名客服人员才能达成目标，例如“80% 的来电在 20 秒内接听”。

合并队列也有局限：当任何服务台都能处理任何条目时效果最好。如果条目需要专家处理，合并的队列可能需要路由规则。

## 活动跟踪

### 活动示例

假设我们有想要跟踪的事物，我们给它起一个通用的名字，例如“活动”（Activity），缩写为“A”。

我们可以高效地使用排队符号来描述该活动以及它如何在队列中流转。

示例：

- Aκ：活动计数：队列中有多少条目。

- Aλ：活动到达率：每单位时间有多少条目进入。

- Aχ：活动离开率：每单位时间有多少条目离开。

- Aδ：活动完成率：每单位时间有多少条目得到服务（无论对错）。

- Aα：活动成功率：每单位时间有多少条目是正确的。

- Aβ：活动失败率，又称错误率：每单位时间有多少条目是错误的。

- Aμ：活动服务率，又称容量：单个服务台在忙碌时每单位时间能完成多少条目。

- Aσ：活动跳过率：每单位时间有多少条目被放弃。

- Aρ：活动利用率：服务台在可用时间中处于忙碌状态的比例，即忙碌时间 ÷ 可用时间，或 λ / (c μ)。

- Aε：活动错误比率：带错误完成的条目与总数之比。

- Aτ：活动前置时间：从请求到完成经过多少时间。

- Aω：活动等待时间：从请求到开始经过多少时间。

- Aφ：活动工作时间：从开始到完成经过多少时间。

- Aθ：活动步进时间：从一次完成到下一次完成经过多少时间。

### 利特尔定律

利特尔定律是约翰·利特尔（John Little）提出的定理：在一个平稳系统中，长期平均顾客数 L 等于长期平均有效到达率 λ 乘以顾客在系统中停留的平均时间 W。

示例符号：

- L：系统中长期平均顾客数。我们更喜欢用 κ（kappa）。

- λ：长期平均有效到达率，即实际进入系统的条目，不包括止步者。

- W：条目在系统中的长期平均时间。我们更喜欢用 τ（tau）。

- L = λ W 即利特尔定律。我们更喜欢写作 κ = λ τ（kappa = lambda \* tau）。

利特尔定律非常普适：无论到达分布、服务分布、服务台数量或队列类型如何，它都成立。

利特尔定律的前提：

- 所有度量单位一致。

- 系统是稳定的，即在测量期间平均到达率等于平均离开率，且开始和结束时的条目数大致相同。

- 提前离开的条目（例如中途离开）要么一致地同时计入 λ 和 τ，要么一致地同时排除。

示例：一个团队平均有 κ = 20 张在制工单，工单以每周 λ = 4 张的速率到达；在稳态下，团队每周也完成 χ = 4 张。因此平均每张工单需要 τ = κ / λ = 5 周。要在不加快工作速度的情况下把前置时间减半，就把在制品减半。

### 关键绩效指标（KPI）

我们通常会跟踪队列中活动的许多方面，并希望从中挑选出与我们项目最相关的少数指标来总结结果。

我们做过很多项目，我们认为最有价值的总结指标是：

- Dτ = 交付前置时间。产品团队可能会说“从概念到客户”或“从想法到实现”。

- Dα = 交付成功率。DevOps 团队可能会说“部署频率”或“我们每天发布 X 次”。

- Dε = 交付错误比率。质量团队可能会说“变更失败率”或“回滚百分比”。

- Rτ = 恢复前置时间。网站可靠性工程师可能会说“失败部署恢复时间”或“平均恢复时间（MTTR）”。

## 服务指标

有用的术语：

- **服务等级指标（SLI）：** 指标本身（例如 99.9% 的正常运行时间）
- **服务等级目标（SLO）：** 该指标的内部目标（例如力争达到 99.95% 的正常运行时间）
- **服务等级协议（SLA）：** 对客户的正式合同承诺（例如 99.9% 的正常运行时间，未达成则有处罚）。

### 平均响应、修复、恢复、解决时间

MTTR 代表四种不同的度量：

| 指标                 | 关注点     | 衡量内容                 | 开始               | 结束               |
| -------------------- | ---------- | ------------------------ | ------------------ | ------------------ |
| **平均响应时间**     | 初始反应   | 确认并开始行动的时间     | 事件被检测/报告时  | 团队开始处理时     |
| **平均修复时间**     | 技术修复   | 修复损坏条目的时间       | 修复工作开始时     | 条目修复完成时     |
| **平均恢复时间**     | 服务恢复   | 恢复全部服务的时间       | 事件/中断开始时    | 服务完全可用时     |
| **平均解决时间**     | 完全解决   | 从检测到关闭的总时间     | 事件被检测时       | 事件完全关闭时     |

**关键区别：**

**响应**衡量团队的准备程度和告警的有效性。响应时间短意味着您的监控和值班流程运作良好，即使实际修复需要更长时间。

**修复**是纯技术性的：一旦开始处理，实际修好损坏的东西需要多长时间？它不包括检测时间、分诊和验证。

**恢复**关注的是从客户角度看的服务可用性。系统可能已经“修复”但尚未“恢复”，比如您仍需要恢复数据、预热缓存或验证功能。

**解决**是最全面的：它涵盖了事件的整个生命周期，从首次检测到事后验证和关闭。

示例场景：

- 凌晨 2:00 — 中断开始
- 凌晨 2:05 — 告警触发，事件被检测到
- 凌晨 2:15 — 值班人员确认并开始处理 → 响应时间：10 分钟（2:05 至 2:15）
- 凌晨 2:45 — 找到根本原因，部署修复 → 修复时间：30 分钟（2:15 至 2:45）
- 凌晨 3:00 — 验证服务对用户正常 → 恢复时间：60 分钟（2:00 至 3:00）
- 凌晨 3:30 — 验证后关闭事件工单 → 解决时间：85 分钟（2:05 至 3:30）

相关指标：

- MTBF（平均故障间隔时间）
- MTTF（平均无故障时间）
- MTTA（平均确认时间）

### DORA 指标

DevOps Research and Assessment（DORA）指标是专门针对软件工程 DevOps 团队的行业标准关键绩效指标（KPI）。参见 [dora.dev](https://dora.dev/guides/dora-metrics/)。

DORA 现在使用五项指标，分为两组。

吞吐量指标：

- **变更前置时间** - 实现、测试和交付某个功能代码所需的时间（从提交到部署到生产环境）。要明确您所说的开始和结束是什么。例如，有些团队喜欢从开发者开始处理工单算起，到开发者把工作推送到持续集成流程为止；这种方法往往更适合衡量个人生产力。

- **部署频率** - 在给定时间段内的部署次数。要明确您所说的部署是什么以及如何跟踪频率。例如，有些团队部署到一组生产服务器并跟踪完整的上线过程，而另一些团队部署到单台用户验收测试（UAT）服务器，并跟踪项目经理何时向用户发送邮件公告请他们试用。

- **失败部署恢复时间** - 从导致生产故障的部署中恢复所需的时间。以前称为平均恢复时间（MTTR）或服务恢复时间。要明确您所说的恢复是什么。例如，有些团队把恢复算作完全解决，即从检测到事件到事件完全关闭的总时间；这种做法更适合称为平均解决时间。

不稳定性指标：

- **变更失败率** - 导致生产故障并需要立即补救（例如回滚或热修复）的部署所占百分比。要明确您所说的失败是什么。例如，有些团队还会在开始处理工单后发现工单信息不足、无法继续，于是把工单退回给规格团队时，也算作一次失败。

- **部署返工率** - 计划外部署所占百分比，例如为修复生产事件而进行的部署。计算方法是计划外部署数除以总部署数。DORA 于 2024 年增加了这项指标。

早期的 DORA 报告还把**可靠性**作为运营绩效指标进行讨论：这是对服务一致性的更广泛、通常是定性的评估，例如可用性、正常运行时间、延迟、准确性和服务等级目标。可靠性有助于表明高速度并不是以牺牲系统能力为代价的。

## 队列的队列

排队论很容易扩展为队列的队列，例如一个包含较低层级阶段、环节或关口的较高层级流程。

### 双钻模型的队列的队列

例如，考虑“双钻”（Double Diamond）创新流程模型，它规定了四个阶段：

1. 发现：理解问题，而不是仅仅假设问题是什么。
2. 定义：借助发现阶段的洞察，定义挑战。
3. 开发：针对明确定义的问题给出不同的解答。
4. 交付：小规模测试不同的方案，然后加以改进。

排队论可以把它建模为一个包含四个阶段队列的流程队列：

- 流程的到达率是阶段 1 的到达率。
- 流程的成功率是阶段 4 的成功率。
- 流程的错误数是各阶段错误数之和。
- 流程的跳过数是各阶段跳过数之和。
- 流程的前置时间是各阶段前置时间之和。
- 流程的最大吞吐量是最慢阶段（即瓶颈）的吞吐量。

### 漏斗式的队列的队列

在实际工作中，我们经常用“漏斗”一词粗略地描述一种在每个阶段都会减少条目数量的队列的队列：

- 招聘队列，包括外联阶段、面试阶段和录用阶段。对于这类队列，我们的目标是最大化阶段 1 的到达率，即扩大外联，例如通过推广。

- 购买队列，包括客户搜索阶段、购物车阶段和支付阶段。对于这类队列，我们的目标是最小化阶段 2 的跳过率，即减少购物车放弃，例如通过提醒。

- 编程队列，包括集成阶段、用户验收阶段和生产上线阶段。对于这类队列，我们的目标是最小化生产上线阶段的错误率，例如通过金丝雀遥测。

## 过劳的恶性循环

当到达率上升时，系统承受的压力更大，也更接近其容量（即 100% 利用率）。这会使周期时间迅速趋向无穷大，在制品也随之增加，进而导致结果更慢。

这催生了业界常见的一种模式，我们称之为“过劳的恶性循环”：当结果差到一定程度，管理者会批准更多资源（例如加班或增派人手），从而提高系统的容量。但系统一旦恢复，管理者就取消加班，过载又重新开始。这个循环可能来得很快，破坏力也很大。解决办法是管理者要花时间去了解系统、容量和利用率。

## 洞见

Bob Wescott（《The Every Computer Performance Book》作者）关于排队论的七条洞见（另见 [Kottke 的总结](https://kottke.org/19/01/its-time-for-some-queueing-theory)）：

1. 服务中心越慢，在峰值负载时应规划的最大利用率就应越低。

2. 任何东西的最后 15% 都很难用上。

3. 越接近极限，犯错的代价就越高。

4. 响应时间的增长受限于能够等待的数量。

5. 记住这是平均值，而不是最大值。

6. 在多个服务中心的情况下，存在人为的否认效应。

7. 用最有利的方式展示小的改进。

## 流程流

流程流是一连串的流程。项目、操作、作业等会沿着流程流向前推进。

例如，一条制造线由若干串联的工位组成，作业从中流过。一家医院包含许多相连的操作序列（入院、病房护理、手术准备、手术、康复等），病人从中流过。一家银行有资金流过的操作序列。理解流是设计和管理高效运营系统的基础。

### 行为参数

一个流程流的行为取决于两个参数：

- 瓶颈速率：流的容量（即利用率最高的流程的速率）。

- 原始流程时间：实体在流中被处理所花费的总时间（即一个实体穿过空流所需的平均时间）。

### 变异性参数

一个流程流的变异性取决于两个参数：

- 流变异性：实体到达系统的间隔时间的变异性。

- 流程变异性：系统中处理时间的变异性。

设想一个同时具有流变异性和流程变异性的流程流。正如预期，从一个工位流出的流的变异性，既取决于流入该工位的流的变异性，也取决于工位自身产生的流程变异性。对两者各自依赖多少，是系统利用率的函数。

变异性是使流程流的表现相对于最佳情况下降的主导因素。因此，理解变异性并找到消除它的方法，是许多运营改进方法论的核心。
